0. IMPLEMENTATION STATUS (NEW in v4)
===============================================================

The VLM pipeline is coded end-to-end. Entry point:
scripts/run_vlm_pipeline.py (--stage all|infer|score). Core logic:
src/vlm_pipeline.py; prompts/schemas: src/models/prompts.py; VLM
backends: src/models/vlm_models.py; dataset loaders + mapping vocab:
src/loaders/dataset_loader.py; taxonomy graph: src/loaders/
excel_loader.py; metrics: src/evaluation/{clip_metrics,taxonomy_metrics}.py.

Key implemented shape (details in the sections below):
  - Two-pass: open caption -> structured extraction (Sections 4-5).
  - Mapping happens in PHASE-1 INFERENCE (not scoring): each extracted
    object is mapped to the taxonomy FIRST, then the VLM labeling call
    is ROUTED (Section 6):
        unmapped        -> ONE full VLM call (nature+biotic+material)
        mapped-nature   -> material-only VLM call (nature/biotic from map)
        mapped non-nature -> NO VLM call
    Every extracted object is labeled on all three axes.
  - --max_hops CLI arg bounds how far an extracted object may resolve
    onto the taxonomy (0 = only annotator-labeled nodes; default 3).
  - --stage all runs infer and score in SEPARATE spawned subprocesses,
    so the VLM's VRAM is released (OS reclaim on process exit) before
    CLIP loads; a shared W&B run id keeps both in one run.
  - Axis scoring differs by dataset type (Section 8): single-label
    (ImageNet/Places) uses the forced top-1 ClipMatch class's taxonomy
    for nature/biotic + VLM material of the best-matching object;
    COCO/BIG-5 use image-level nature (OR) + matched-object axes.

1. TWO SEPARATE PIPELINES (KEY TERMINOLOGY)
===============================================================

  A) VLM PIPELINE (language-based; IMPLEMENTED — see Section 0):
     1. Open-ended caption generation
     2. Structured object extraction
     2b. Map each extracted object to the taxonomy (WordNet mapping
        vocab) BEFORE labeling — routes the labeling call (Section 6)
     3. Taxonomy labeling (nature/no-nature, biotic/abiotic,
        material/immaterial) — mapping when possible, VLM reasoning
        otherwise, routed per object (see Section 6)
     Produces a full per-image prediction scoreable with standard
     accuracy/precision/recall/F1, same framework as the closed-set
     baselines already built.

  B) GROUNDING PIPELINE (geometric/embedding-based; designed, not
     yet implemented):
     1. Thing/stuff geometric routing — Grounding DINO 1.5 + SAM
        for discrete objects ("things"); CLIPSeg-style dense
        segmentation for amorphous regions ("stuff"). Routing is
        geometric (boundable vs amorphous), NOT taxonomic —
        material/immaterial does not align with thing/stuff (e.g.
        a stuffed rabbit is immaterial but geometrically a "thing")
     2. Dual-branch verification — detector/segmenter confidence +
        hierarchy-based margin check via FG-CLIP2 (cosine similarity
        across target/hypernym/sibling hyponyms on localized crops).
        CAVEAT (v6): FG-CLIP2 was tried for the VLM pipeline's CLIP
        scoring and abandoned — its trust_remote_code __init__ crashes
        with a meta-tensor error under this project's transformers
        version (Section 11). Re-verify it loads at all before building
        this step around it; may need a different CLIP backend here too.
     3. Taxonomy-attribute spatial aggregation — per-object
        localization maps combined into biotic/abiotic and
        material/immaterial heatmaps.
        OPEN QUESTION (raised by Pau): worth reassessing whether
        this is actually valuable to implement, vs. lower priority
        than the other Grounding pipeline components — not yet
        decided either way.
     4. Nature importance score (NEW): once nature-related elements
        are segmented via CLIPSeg/SAM, compute the fraction of
        total image pixels belonging to nature-related segments —
        a 0-to-1 score reflecting how much of the image nature
        occupies. Proposed refinement (not yet designed): weight
        central pixels more heavily than peripheral ones, on the
        reasoning that centrally-placed content is more likely to
        be the compositional focus of the image. Exact weighting
        scheme (e.g. distance-from-center falloff function) still
        to be defined.

The rest of this document is organized around the VLM pipeline
(Sections 2-8), since that's what's actively being built. The

3. SERVING / FRAMEWORK DECISIONS
===============================================================

- Context files go in the "system" role (fixed, cacheable,
  behavioral), not "user" (variable, per-call, read as a request).
- vLLM prefix caching (--enable-prefix-caching) to be confirmed ON
  with Ramin — makes the always-present protocol cheap at 2M-image
  scale rather than reprocessed every call.
- Different system prompts per stage = different cache prefixes
  (fine; confirm Ramin's serving config allows this).
  IMPLEMENTED: three distinct system prompts — caption/extraction
  (nature definition only), unmapped-labeling (all three definitions),
  mapped-nature material-only labeling (material definition only) —
  so each is a stable, separately-cacheable prefix.
- Files read from disk once at startup, not per-call, so the token
  sequence stays stable (identical string = cache hit).
  IMPLEMENTED: build_system_prompts() reads the definition files once
  in phase_infer; run_inference reuses the fixed strings per batch.
- IMPLEMENTED (VRAM): --stage all runs infer and score in separate
  'spawn' subprocesses. When the infer subprocess exits, the OS
  reclaims the VLM's GPU memory in full before CLIP loads — more
  reliable than the earlier in-process unload_vlm (vLLM/torch do not
  release CUDA memory dependably on GC). Only the picklable args
  Namespace crosses the boundary; a shared W&B run id (resume="allow")
  keeps both subprocesses logging into one run.
- DSPy: protocol text maps to a Signature's "instructions" field;
  underlying calls still hit vLLM, caching still applies.
- Need to empirically verify smaller models (e.g. Qwen3.5-0.8B)
  actually follow system-prompt instructions reliably — not
  assumed, to be tested.

4. VLM PIPELINE — CAPTIONING STRATEGY (BASELINE)
===============================================================

- BASELINE = two-pass: fully open-ended caption generation (no
  schema at all) → separate call for structured extraction.
  Chosen over single-pass-with-schema-from-the-start because
  forcing structure immediately risks collapsing the caption into
  a checklist-style output, which would make the faithful
  F-CLIPScore and Object-CLIPScore metrics converge and stop being
  meaningfully different.

- Caption prompt (baseline, NEUTRAL — no nature-priming).
  ORIGINAL DESIGN (v1-v6 of this recap): "Describe this image in 3-4
  sentences, covering the main subject, the background, the setting,
  and any secondary elements present. Be specific but concise."
  Reasoning: plain "describe the scene" suffers from (a) salience
  bias (only prominent subject described) and (b) brevity bias
  (short captions leave no room for secondary elements). This prompt
  addresses both without leading toward nature specifically.
  SUPERSEDED (v7 — CLAUDE.md updated to match): the shipped baseline
  is now the shorter "Describe this image, including any text."
  (src/models/prompts.py CAPTION_PROMPT), a deliberate change to
  cover BIG-5's text-heavy/meme/screenshot images (a bare "describe
  this image" skips on-image text entirely). The salience-bias/
  brevity-bias mitigation the original 3-4-sentence prompt provided
  is NOT carried over by this shorter prompt — not yet re-validated
  empirically post-switch; worth confirming via F-CLIPScore/
  Object-CLIPScore whether that mitigation is still needed once
  real per-model captions are in hand.

- Explicit decision: do NOT add "pay special attention to nature-
  related elements" to the baseline. Reasoning: leading question →
  risk of hallucinated compliance (model invents nature-adjacent
  content because it was asked to look for it) — directly relevant
  since this is the exact failure mode F-CLIPScore/OHD-Caps
  research targets. Nature bias already present via the system-
  level definition file.
  → Proposed as an ABLATION axis instead (Section 7), to be
  settled empirically via F-CLIPScore/Object-CLIPScore rather than
  assumed.

5. VLM PIPELINE — EXTRACTION STRATEGY
===============================================================

Two ways to do extraction — both planned as part of the ablation
study, undecided which is default:
  a) same VLM does both caption + extraction (multi-turn) —
     simpler, faster to ship, but conflates visual understanding
     quality with instruction-following/schema-adherence quality.
     ADDED BENEFIT (Pau): re-sending the image to the VLM during
     the extraction call gives the model a second look, which may
     surface objects omitted from the free-form caption the first
     time around.
  b) caption by VLM, extraction by a separate fixed agnostic LLM
     (constant across all VLMs benchmarked) — decouples visual
     perception from extraction compliance, cleaner for the Goal-1
     cross-VLM comparison.
Plan: build (a) first for week-1 speed, formally compare vs (b)
once the pipeline exists.
IMPLEMENTED: (a) — the same VLM captions and extracts (extraction
re-sends the image, the "second look"). (b) remains an ablation
(Section 7), not yet built. Extraction uses a structured schema
(ObjectExtractionResponse) returning a de-duplicated object list.

CONSTRAINT ON THIS ABLATION: material/immaterial labeling
(Section 6) cannot be handed to a text-only agnostic LLM regardless

Places) — worth checking extraction-hit rate and the hP/hR mapping-
failure rate on Places before/after this change.

6. VLM PIPELINE — TAXONOMY LABELING STRATEGY
===============================================================

Hybrid approach, applying the pre-existing project principle that
biotic/abiotic (and nature/no-nature) is inheritable via WordNet
hop distance, while material/immaterial is NOT (depends on
real-instance-vs-representation — requires per-instance reasoning,
not just concept lookup):

  - NATURE/NO-NATURE and BIOTIC/ABIOTIC: use WordNet mapping when
    the object falls in the mapped vocabulary (ImageNet/COCO/
    Places); fall back to VLM reasoning when unmapped. Applies to
    BOTH axes equally — both are hop-derivable from a mapped GT
    node.

  - MATERIAL/IMMATERIAL: ALWAYS use VLM reasoning, never mapping —
    a "tree" node has no way of encoding whether THIS image shows
    a real tree, a painting, or a video-game tree. No mapping-based
    alternative exists for this axis.

  - IMPORTANT: VLM labeling is IMAGE-SUPPORTED, not text-only — the
    model has the image available when doing the labeling
    reasoning, not just the extracted object string. Specifically
    crucial for material/immaterial (a bare word "tree" cannot
    disambiguate real/painted/video-game; the pixels can). Drives
    the constraint in Section 5 — material/immaterial can't be
    delegated to a text-only agnostic LLM.

IMPLEMENTED (routing + where it runs):
  Mapping runs in PHASE-1 INFERENCE, BEFORE the VLM labeling calls
  (not deferred to scoring — saves compute and the artifact ships
  fully resolved). Each extracted object is mapped via the dataset's
  authoritative class->synset table (build_mapping_vocab; no
  word-sense guessing), then the labeling call is ROUTED:
    - UNMAPPED object -> ONE full VLM call, all three axes at once
      (TaxonomyResponse; system prompt = all three definitions).
    - MAPPED-nature object -> MATERIAL-ONLY VLM call (MaterialResponse;
      system prompt = material definition only). nature/biotic taken
      from the mapping, so the VLM is not asked to re-derive them.
    - MAPPED non-nature object -> NO VLM call (nature=False from the
      map; biotic/material are n/a).
  Two batched generate_batch calls per image-batch (one per system
  prompt) keep each prefix cache-friendly. EVERY extracted object ends
  up labeled on all three axes.

  --max_hops (CLI) bounds how far an extracted object may resolve onto
  a labeled taxonomy node (TaxonomyGraph.resolve_labels): 0 = only a
  directly-annotated synset counts (no inherited label); 1 = also one
  hypernym/hyponym hop; default 3. Stored in the artifact header and
  reused by --stage score. Lower values push more objects to the VLM
  fallback; higher values map more aggressively.

VALIDATION / CALIBRATION:
  Rather than an ablation comparing "mapping-first" vs "always use
  VLM," directly measure classification calibration: have the
  model classify GT-mapped CLASS NAMES ONLY (no image, no
  extraction involved) against the WordNet-derived labels for
  nature/no-nature and biotic/abiotic. This isolates pure
  taxonomic-reasoning reliability from object-recognition ability,
  and gives a clean number for "how much can we trust VLM fallback
  when mapping is unavailable."
  ASSUMPTION TO STATE EXPLICITLY: this assumes reliability on
  canonical dataset class names transfers to messier real-world
  BIG-5 objects — a transfer assumption, not proven by the check
  itself.

THREE DISTINCT ACCURACY LAYERS (do not collapse into one number):
  1. Extraction accuracy — did the GT object get mentioned at all
     (Section 8a-c)
  2. Classification calibration — class name → taxonomy label vs
     WordNet GT, no image, no extraction (this section, above)
  3. End-to-end mapped-subset accuracy — full image pipeline,
     filtered to GT-mapped classes (compounds extraction quality +
     classification quality; reflects real-world pipeline behavior,
     NOT a clean reasoning-only number — the mapped subset's
     accuracy still depends entirely on whether the model correctly
     identified the element in the image first)
  Report all three separately, clearly labeled — they answer
  different questions and conflating them hides which part of the
  pipeline (recognition vs reasoning) is responsible for errors.

8. METRICS FOR VLM PIPELINE SELECTION
===============================================================

--- Reference-free (fast iteration, any image, no GT needed) ---

a) F-CLIPScore (faithful replication, Oh & Hwang — "Vision-
   Encoders (Already) Know What They See" / F-CLIPScore paper):
     F-CLIPScore(S) = [CLIPScore(S) + sum_i CLIPScore(n_i)] / (N+1)
   S = full caption sentence, n_i = individual extracted objects
   (N of them). Requires the caption (sentence term). NOT novel to
   us — cite exactly as their method when implemented per Eq. 1.

b) Object-CLIPScore (OUR variant, F-CLIPScore-INSPIRED, NOT
   identical — must be described precisely, never called
   "F-CLIPScore"): average CLIPScore over extracted objects ONLY,
   template "a photo of a {object}", NO sentence-level term. Their
   ablations never test dropping the sentence term — must be
   attributed as an adaptation. Underlying object-level insight is
   theirs (cited); the specific simplified formula is ours.

KNOWN LIMITATION (inherited, not introduced by us): CLIPScore-family
metrics compare against the WHOLE image embedding, not a localized
crop — a plausible-but-absent object can score deceptively well.
Even the original paper's best untrained noun-level variant trails
trained methods by 17.6-37.4 points on OHD-Caps. Explicitly
first-pass proxies, not substitutes for the Grounding pipeline's
localized verification.

CRITICAL PRACTICAL ISSUE — CLIP 77-TOKEN LIMIT:
Standard CLIP text encoders truncate at 77 tokens; only ~20 tokens
reliably well-trained per Long-CLIP's analysis. Conflicts with the
detailed-caption strategy (Section 4) for the sentence-level term.
Object-level terms unaffected (short templated phrases).
Mitigation options (not yet decided):
  - Long-context CLIP variant for the sentence-level term. FG-CLIP2
    was tried (it explicitly trains on long-caption modeling, unlike
    vanilla CLIP) and ABANDONED — see Section 11 — its
    trust_remote_code __init__ crashes with a meta-tensor error under
    this project's transformers version. Jina-CLIP-v2 (now in
    CLIP_PRESETS) handles much longer text and may be worth trying
    for this specifically; alternatively Long-CLIP (still not
    packaged as a plain HF AutoModel — see CLIP_PRESETS's comment).
  - Accept + document truncation as a stated limitation
  - Deliberately truncate/cap captions at a controlled length

F-CLIPScore/Object-CLIPScore reward PLAUSIBILITY, not
EXHAUSTIVENESS — insufficient alone to pick the final config (a
pipeline extracting only a few "safe" objects can score well while
missing most real content). ADDED (Pau): for this reason, track and
report the TOTAL NUMBER of objects detected/extracted per model as
a companion diagnostic — a model scoring well on F-CLIPScore/
Object-CLIPScore while extracting very few objects overall is a
red flag for under-extraction, not a sign of a well-calibrated
pipeline. Must be paired with GT-based checks below (two-tier
validation: cheap proxy for broad iteration, GT checks to confirm
the winning configuration).

--- GT-based (confirm final configuration) ---

c) BIG-5 nature Yes/No accuracy: map extracted objects through
   WordNet; nature=1 if ANY object maps to a nature node, else
   nature=0. Compare against the BIG-5 GT annotations (image-level,
   usable even without a full object dictionary mapped). Report
   OBJECT-MAPPING HIT RATE (% of extracted objects that map to
   WordNet at all) alongside it as a diagnostic — low hit rate
   means "no nature" errors may reflect vocabulary-mapping gaps,
   not genuine model failure to notice nature.

   EXTENDED (Pau): since the VLM pipeline includes a VLM fallback
   for unmapped objects by design (Section 6), this fallback can be
   used from the start, not just as an unmapped-case patch — every
   extracted object gets a nature/no-nature, biotic/abiotic, and
   material/immaterial label regardless of mapping status (mapped →
   WordNet-derived label; unmapped → VLM-derived label). This means
   full accuracy — not just nature Yes/No, but also biotic/abiotic
   and material/immaterial — can be computed across ALL datasets
   (BIG-5, COCO, ImageNet, Places), not only where mapping succeeds.
   Track WordNet-mapping-rate vs. VLM-fallback-rate throughout, so
   it's always clear how much of any reported accuracy number rests
   on deterministic mapping vs. VLM judgment.

d) COCO/ImageNet/Places — GT-mention accuracy (EM/Contains, per
   Ging et al.'s O-VQA framework, applied to extracted-object-lists
   instead of free text — cite as such): check whether the GT class
   or any WordNet-synset synonym (not just the literal label
   string) appears among extracted objects.

e) ClipMatch (Ging et al.-inspired), ImageNet + Places ONLY —
   COCO/BIG-5 excluded (COCO multi-label, BIG-5 has no closed class
   vocabulary — ClipMatch needs a fixed candidate list, so this
   scoping is a correctness requirement, not a compromise):
     - SUPERSEDED IN v5 (see below): originally run against the
       EXTRACTED OBJECT LIST (max similarity across independently-
       embedded objects per candidate) with the raw-caption and
       concatenated-object-sentence variants explicitly REJECTED for
       token-limit + semantic-dilution reasons (kept below for
       history). After both variants were actually implemented and
       compared empirically, the CAPTION-based version performed
       better — so as of v5 it is the ONLY ClipMatch implementation;
       the object-list code has been removed from clip_metrics.py.
     - CURRENT (v5): score the WHOLE CAPTION's CLIP embedding
       against each candidate class directly; argmax = predicted
       class (clip_metrics.clipmatch). The 77-token truncation risk
       this reintroduces (see the original rejection rationale below)
       is accepted as a stated limitation given the empirical gain.
     - ORIGINAL (v1-v4) DESIGN, kept for history — run against the
       EXTRACTED OBJECT LIST, not the raw caption and NOT a
       concatenated sentence template ("a photo of a X, a Y, and a
       Z" was considered and rejected — see below):
         - Score each extracted object independently via its own
           short phrase ("a photo of a {object}"), take the MAX
           similarity across all objects as the model's implicit
           best guess for each GT candidate class.
         - REJECTED APPROACH — raw caption: risks CLIP 77-token
           truncation on long captions, and ClipMatch was designed/
           validated on short single-answer VQA responses, not
           multi-sentence scene descriptions — using the full caption
           deviates from how the metric was built and tested. (This
           is the approach v5 above ended up adopting anyway, after
           empirical comparison showed it outperforming the
           object-list version despite this caveat.)
         - REJECTED APPROACH — concatenated object-list sentence ("a
           photo of a X, a Y ... and a Z"): (1) still risks the
           77-token limit with busy scenes (8-10+ objects), worse
           than the caption case since triggered by object count not
           verbosity; (2) semantic dilution — one joint embedding for
           many objects is a smeared average, diluting the signal for
           any single target GT class, hurting matching precisely in
           richer scenes. (Still not used — this rejection stands.)
     - CANDIDATE-SIDE text (v11, OPT-IN, separate from all of the
       above — those are all about the IMAGE-description side):
       `--use_wordnet_definitions_clipmatch` swaps each GT candidate
       class's plain OBJECT_TEMPLATE phrase ("a photo of a golden
       retriever") for its WordNet lemma(s) + gloss in natural prose
       (clip_metrics.wordnet_definition_text — "A golden retriever,
       also known as ... . It is defined as: <definition>."). NOT the
       default; not yet empirically validated either way. See
       RESOLVED/PROPOSED IN v11, Section 11.

f) Hierarchical Precision / Recall (hP/hR) + Wu-Palmer, per
   Snæbjarnarson et al.'s taxonomy-aware evaluation — ImageNet +
   Places ONLY (same scoping rationale as ClipMatch, e above):
     - Captures GRANULARITY CREDIT that EM/Contains cannot: e.g.
       predicting "canine" when GT is "golden retriever" scores
       flatly wrong under Contains, but hP/hR gives partial credit
       for the correct branch of the tree.
     - Directly demonstrates (rather than just cites) the
       granularity-mismatch failure mode already discussed in the
       SOTA review (Yu et al.'s fine-grained-task finding).
     - Method: take the predicted GT class from ClipMatch (e,
       above), then map it onto a WordNet node via the extracted
       object list and compute hP/hR against the GT node.
     - IMPLEMENTED (taxonomy_metrics.resolve_to_wordnet): the
       predicted-class -> WordNet-node step is NOT a BGE cross-encoder
       (that was the design sketch). Instead the extracted objects are
       ranked by their CLIP similarity to the predicted class (each
       extracted object's embedding dotted against the ClipMatch-
       predicted class's own embedding — computed in run_vlm_pipeline.py
       right after the v5 caption-based ClipMatch call, since ClipMatch
       itself no longer touches per-object embeddings), the top phrase
       that resolves in WordNet is taken, and polysemy is broken by
       maximizing Wu-Palmer similarity to the predicted class. hP/hR
       are then the ancestral-closure overlap of GT node vs. predicted
       node (compute_hierarchical_metrics).

g) COCO MASK-IoU DETECTION EVALUATION (NEW in v21, IMPLEMENTED; MASK-ONLY as
   of v22 — see RESOLVED IN v22 below, box matching is GONE, not an option;
   ENTITY-GRANULARITY-ONLY as of v24, with an IoU sweep as its headline and
   pixel coverage deleted — see RESOLVED IN v24, which supersedes several
   paragraphs below and is the authority where they disagree) —
   src/evaluation/detection_metrics.py, driven from run_vlm_pipeline.py's
   --stage score. COCO ONLY, and only on an artifact the Grounding pipeline
   enriched with INSTANCE grounding. Runs ALONGSIDE the lexical axis metrics
   in the IMPLEMENTED block below, never replacing them.

   WHY THE INSTANCE HEAD IS STILL READ, EVEN THOUGH SCORING IS ENTITY-LEVEL.
   Everything else in the Grounding pipeline reads SAM3's semantic_seg, which
   is concept-level: one mask for "cow", however many cows. COCO's GT is
   per-instance, so evaluating against it needs pred_masks/pred_boxes/
   pred_logits — and, critically, the instance head is also what supplies the
   per-entity CONFIDENCE score (max over an entity's instances) that AP ranks
   by. Both heads come off the SAME forward pass, so this is a post-processing
   cost, not a second run. v24 note: the instance masks are now UNIONED per
   extracted entity before matching, so instance granularity survives only as
   an intermediate representation, never as a reported number — see RESOLVED
   IN v24 for why instance-level scoring was measuring the wrong thing.

   MATCHING IS CLASS-AGNOSTIC — the one substantive departure from the v1
   design sketch, and the reason the whole thing is worth building. Standard
   detection evaluation only pairs a prediction with a GT box when their
   CLASSES already agree. Under that protocol a predicted "bull" against a GT
   "cow" is counted as a false positive AND a false negative, and the pair
   never reaches the label metrics at all — which throws away exactly the
   granularity-mismatch case hP/hR exist to measure (see f, above, and the
   Yu et al. fine-grained finding in the SOTA review). So assignment uses
   MASK overlap only (Hungarian, one-to-one, maximizing total IoU, IoU >= 0.5
   by default — v22: masks, never boxes; see RESOLVED IN v22 below), and the
   class comparison happens afterwards, on the pairs the
   geometry produced. CONSEQUENCE TO STATE WHEN REPORTING: precision/recall/
   F1/AP from this block measure LOCALIZATION alone. They are NOT "detected
   the right thing" — that half is the label metrics, reported separately and
   never merged into one number, for the same reason §9 keeps GT-recovery and
   verified-extra-content separate.

   Hungarian rather than the usual greedy highest-IoU-first loop: greedy can
   strand a GT box whose only above-threshold partner was claimed by a
   marginally better earlier pairing, understating recall on crowded images,
   which COCO has many of.

   WHAT IS SCORED AGAINST WHAT:
     - GT is restricted to NATURE-mapped COCO classes, because the Grounding
       pipeline only ever grounds nature-labeled entities. A "car" GT box
       could not be matched by any pipeline behavior whatsoever, so counting
       it as a false negative would measure the protocol, not the model.
     - An UNMATCHED PREDICTION is a false positive only when its own phrase
       names a class in that evaluated vocabulary; otherwise it is EXCLUDED —
       counted and reported as excluded_predictions, but not charged against
       precision. This is the v1 design's own rule ("COCO's 80 classes are a
       curated subset, so an extra real object is not a hallucination"),
       tightened: the original said exclude ALL unmatched predictions, which
       would also excuse a genuinely hallucinated "dog" on a dog-free image.
       The vocabulary tested against is the EVALUATED one (nature-mapped),
       not all 80, and it must be filtered identically to the GT boxes — the
       two agreeing is what makes the rule symmetric rather than a loophole.
     - iscrowd regions are neither required to be detected nor charged as
       false positives when a prediction lands inside one (COCO's own
       convention). Suppression uses intersection over the PREDICTION's area,
       not IoU — a crowd box dwarfs any single prediction, so IoU would stay
       near zero even for a prediction sitting entirely inside it.
     - NO TRUE NEGATIVES, therefore no accuracy. Detection has no finite
       negative class to be correct about; the space of boxes not predicted
       is unbounded. This is a deliberate departure from the axis metrics,
       which do report accuracy because their negative class is real.
     - TAXONOMY-DISAGREEMENT DIAGNOSTIC (added on Pau's question "does a
       nature predicted bbox ever get associated with a non-nature target
       class?"). By construction it can never be a TRUE POSITIVE — non-nature
       GT is filtered out before matching — so before this was added the case
       fell straight through to `excluded` and became invisible,
       indistinguishable from a box over empty background. Those are very
       different things, so the non-nature GT boxes are now kept (unmatched,
       unscored) purely to detect the overlap, and every such hit is reported
       in its own dict with a per-GT-class and per-predicted-entity
       breakdown. It does NOT alter tp/fp/fn: the prediction stays in
       whichever bucket the normal rules gave it, so precision/recall have
       exactly the same definition with the diagnostic on or off and runs
       stay comparable. WHY THIS MATTERS FOR THE THESIS rather than being a
       mere debug counter: it is the Nature-Based Artefacts clause made
       measurable. COCO's `dining table` NODE resolves to non-nature, but the
       nature definition explicitly counts a wooden table whose grain is
       visible AS nature, and a class node cannot encode whether THIS image
       shows oak grain or painted MDF — the identical concept-vs-instance
       argument already accepted for material/immaterial and for routing
       mapped-non-nature objects to the VLM (Section 6). So a hit here is
       frequently NOT a model error, and the per-class breakdown is what
       separates the two readings: wood/stone furniture classes dominating
       says that clause is firing on real instance evidence, while a flat
       spread of unrelated classes says the boxes are simply loose.
     - AP@0.50 and AP@[.50:.95] (101-point interpolated, class-agnostic),
       re-matching at each rung of COCO's IoU ladder off one cached IoU
       matrix. Excluded and crowd-suppressed predictions are kept OUT of the
       AP ranking — feeding them in as negatives would reimpose precisely the
       penalty the exclusion rule removes.

   LABEL SCORING (per matched pair only — naming quality is undefined where
   nothing was localized): BOTH views, as this document has argued for
   EM/Contains vs hP/hR throughout.
     - EXACT MATCH, using the same surface-form test as the extraction-hit
       diagnostic (class name or any WordNet lemma of its synset, whole
       phrase or trailing SPAN — not just the trailing single word), so
       "named it correctly" means one thing across the whole codebase. The
       span generalization matters for any GT term longer than one word: the
       old single-trailing-word check matched "huge cow" against "cow" fine,
       but missed "huge potted plant" against "potted plant" (its trailing
       WORD is just "plant"). Anchoring at the phrase's END, not anywhere
       inside it, is what still correctly rejects "cow shed" against "cow" —
       English noun phrases are right-headed, so the entity's own name is
       always the trailing span, never a leading modifier.
     - HIERARCHICAL: hP/hR/hF1 + Wu-Palmer between the GT synset and the
       predicted phrase's synset. Measured: "bull" against a GT "cow" scores
       hF1 ~0.94 and Wu-Palmer ~0.94, versus 0.27 against "airplane" — the
       graded credit the exact-match view scores as flat zero. Reported
       pooled (resolution failures counted as 0.0) and resolved-only, each
       mean ± population std, matching the ImageNet/Places convention in f.
     - AXIS AGREEMENT (biotic/material only): the matched predicted entity's
       own hybrid label vs the GT box's taxonomy position, off the SAME box
       correspondence — a tighter binding than the lexical matching the plain
       COCO axis metrics use, since it's tied to a specific instance rather
       than "the first same-named object in the image". NATURE is excluded on
       purpose: every matched pair here is nature-vs-nature by construction
       (only nature entities get grounded, and GT is nature-restricted for
       this eval), so a reported agreement rate for it would be a tautology,
       not a measurement.

   NO GT LEAKAGE — the part most easily got wrong. Resolving the predicted
   phrase to a WordNet node needs word-sense disambiguation, and the one
   anchor available here is the GT class of the box it was matched to. Using
   it would resolve an ambiguous phrase toward whichever sense the GT happens
   to be, inflating the very hP/hR it feeds. (Contrast resolve_to_wordnet's
   own anchored use in f: there the anchor is ClipMatch's PREDICTION, so a
   wrong anchor drags the score down, not up — which is why that one is
   safe.) So the anchor is deliberately withheld
   (resolve_phrase_to_wordnet(phrase, anchor_synset_id=None)) and senses fall
   back to WordNet's most-frequent-sense ordering. ONE correction to bare MFS,
   found while testing and worth recording because it would have been a silent
   quality problem rather than a visible bug: WordNet's first two senses of
   "crane" are the writers Stephen and Hart Crane, so an entity a segmenter
   found in a photograph would have resolved to a dead American poet and been
   scored against that branch of the tree. INSTANCE synsets (proper nouns,
   identifiable by having instance_hypernyms) are therefore deprioritized on
   the anchorless path — a GT-independent test, so still no leakage, and it
   only reorders, never empties, so a genuine proper noun still resolves.

   GT PLUMBING: load_coco now stores per-instance gt_boxes (xyxy, converted
   once from COCO's native xywh) alongside the existing class-collapsed
   targets — the two views answer different questions and neither replaces
   the other. dataset_loader.coco_gt_boxes back-fills them at SCORING time
   from --instances_json, keyed by file name, so an artifact produced before
   this existed can be scored without paying for COCO-scale inference again.

   NOT YET VALIDATED ON REAL DATA. The logic is covered by 143 checks over
   synthetic boxes/records (geometry, Hungarian vs greedy, the crowd and
   curated-vocabulary rules, AP edge cases, mask->bbox exclusivity, the
   anchorless-resolution regressions, and the cow/bull case end to end), but
   no real SAM3 COCO run has been scored with it. Treat the first real
   numbers as a calibration exercise: --instance_score_threshold in
   particular (SAM3's own 0.3 default) directly trades detection precision
   against recall and has not been tuned on this data.

Report BOTH EM/Contains (strict) and hP/hR (graded closeness) per
dataset — they answer different questions; together they give a
richer results table (exact-match rate + how far off misses were)
than either alone.

IMPLEMENTED — AXIS SCORING (nature/biotic/material acc/P/R/F1),
SPLIT BY DATASET TYPE:
  - ImageNet/Places (single-label): nature/biotic are read off the
    FORCED top-1 ClipMatch class's taxonomy position — NOT lexical
    extraction matching, NO similarity threshold (global argmax over
    the full candidate vocab always returns a class). This fixes a
    real bug: ORing nature across every extracted object penalized a
    correctly-detected incidental object (e.g. a real cat in a
    GT-"couch" image). Robust to species-level mismatch (GT "golden
    retriever" vs. pred "dog" still agree on nature/biotic).
    material stays the VLM's own label (never mapped, per this
    section's rule) — taken from the best-matching extracted object.
  - COCO (multi-label) + BIG-5 (holistic scene): image-level nature =
    OR over extracted objects; biotic/material scored on the matched
    GT object (lexical class-name/synonym match).
    DONE IN v21 (this was the "FUTURE WORK (needs the Grounding pipeline)"
    item, and the TODO that sat in run_vlm_pipeline.py): box-IoU assignment
    now EXISTS — see Section 8g for the built design, which differs from the
    sketch this paragraph used to contain in three ways worth noting. (1) The
    boxes come from SAM3's instance head, not Grounding DINO 1.5 (dropped
    with the thing/stuff split). (2) It does NOT replace the lexical matching
    here; it runs alongside it, because lexical matching is all a VLM-only
    COCO artifact can support and the two answer different questions.
    (3) Matching is class-agnostic and the "unmatched predictions excluded"
    rule is narrowed to predictions naming no evaluated class — the blanket
    version would also excuse a genuinely hallucinated "dog".
  - "extraction-hit rate" (exact-match: was the GT object mentioned)
    is kept as a REPORTING-ONLY diagnostic; it no longer gates or
    feeds any axis score.

RESOLVED IN v24 (decided per Pau, after reading the first full gemma-4-12B-it
COCO numbers and finding two of the three reported blocks actively
misleading):
- INSTANCE-LEVEL DETECTION IS REMOVED. score_image_detection is deleted, not
  deprecated; summary["detection"] is now the ENTITY-level block (the old
  summary["detection_entity"] namespace is gone, folded into the primary
  name). Pau's reasoning: what this pipeline actually predicts is a CONCEPT
  ("orange slice"), grounded by SAM3 into however many masks, while COCO
  annotates individual objects — so instance matching was measuring an
  artifact of that mismatch, not model quality. The numbers made it concrete:
  instance-level precision 0.358 vs entity-level 0.909 on the SAME
  predictions, the gap being SAM3's undeduplicated duplicate queries plus
  COCO's non-exhaustive annotation of crowded scenes. Both distortions vanish
  under the union by construction. ACCEPTED COST, unchanged from v21: no
  per-object counting ("found 8 of 12 cows"). Consequences: --instance_nms_iou
  is removed as DEAD (a union is bit-identical with or without suppression);
  the GEOMETRIC half of the false-positive test
  (entity_matched_elsewhere_in_image) is removed because at entity granularity
  each entity appears exactly once and it could never fire; the
  taxonomy-disagreement diagnostic was PORTED to entity level (non-nature GT
  merged per class, matching the evaluation's own granularity) rather than
  lost with the block that used to compute it.
- PIXEL COVERAGE IS REMOVED (summary["detection_pixels"], pixel_stats,
  pixel_summary). Pau called it misleading and it provably was, for a reason
  worth recording so it is not rebuilt the same way: its by_gt_class view
  accumulated ONLY matched TP pairs plus wholly-missed GT classes, and never
  the unmatched/excluded predictions — so per-class pixel_precision/pixel_iou
  structurally excluded the single dominant source of imprecision, while the
  whole-image mean_image_iou included all of it. The two could not be
  reconciled and invited exactly the question that surfaced this ("how can the
  WORST class be 0.51 when the mean image IoU is 0.32?"). The honest fix and
  the flattering fix pointed in opposite directions, and the IoU sweep below
  answers the underlying question ("how well do the masks trace the objects")
  without the ambiguity, so the block was dropped rather than patched.
- THE HEADLINE IS NOW AN IoU SWEEP (detection_metrics.sweep_summary,
  summary["detection_iou_sweep"]): precision/recall/F1 recomputed at every rung
  of COCO's ladder off ONE cached IoU matrix, each rung getting its own
  independent matching pass (a pair clearing 0.50 need not clear 0.75).
  Reported at @0.50, @0.75 and @[.50:.95]. The SHAPE of that curve is a direct
  readout of MASK TIGHTNESS — an F1 that holds from 0.50 to 0.75 means the
  masks trace their objects, one that collapses means blobs that only just
  cleared the permissive threshold — which is precisely what neither the old
  single operating point nor pixel coverage could show.
- AP IS KEPT BUT REFRAMED, because the request that prompted this round
  ("precision, recall and f1 for AP@.5, 0.75 and 0.5:0.95") conflated two
  different instruments, and the code now documents the distinction at every
  point of use. AP varies the CONFIDENCE cutoff at fixed IoU and integrates the
  PR curve (is SAM3's ranking informative?); the sweep varies the IoU
  THRESHOLD at a fixed prediction set (are the masks tight?). AP is NOT a
  stricter F1, and F1@0.75 is NOT "AP at 0.75". Also recorded: AP is bounded
  by max achievable recall, so AP@0.50 (0.766) sitting below F1@0.50 (0.852)
  is expected, not a bug; and it is AP, never mAP — matching is class-agnostic
  by design, so there is no per-class axis to average over.
- EXCLUDED PREDICTIONS MUST BE QUOTED WITH PRECISION. Measured on this run:
  5727 of 7539 entity predictions (76%) named nothing in COCO's evaluated
  vocabulary — tree, sky, grass, water — and were exempted. Entity precision
  0.909 therefore describes only the 24% COCO can adjudicate, and is NOT "91%
  of our masks are good". The console now prints that ratio directly beneath
  precision so the number cannot be read without its denominator. Recall
  carries no such caveat.

RESOLVED IN v22 (decided per Pau, after the first real COCO run):
- Box-IoU matching is REMOVED — not deprioritized, not kept as an option
  behind a flag, gone. There is no --detection_iou_type anymore; detection
  matches on MASKS, full stop. Reasoning Pau gave: this pipeline's actual
  output IS a mask (SAM3's instance head), and COCO ships per-instance
  `segmentation` for every annotation — so matching on boxes was measuring the
  wrong thing from the start. It briefly shipped as a --detection_iou_type
  mask|box toggle (mask default, box kept "for comparability"), then removed
  entirely once real numbers made the gap concrete: two crossing diagonal
  strokes score box IoU 1.000 (a "perfect match") and mask IoU 0.000 — a box
  around a curled-up dog is mostly the sofa behind it, and two masks that
  overlap poorly can share a nearly identical box. Keeping a toggle around
  would have implied box matching was a legitimate, if lesser, choice; it
  isn't one for this pipeline.
- GT segmentation is loaded from --instances_json UNCONDITIONALLY now (COCO's
  segmentation is deliberately never stored in the artifact — it would bloat
  every record for a scoring-only use). Missing --instances_json means
  detection is skipped outright with a clear message, never a silent
  downgrade to box matching — the same principle as removing the flag.
- Every per-pair/FP/excluded/missed-GT row in the predictions CSV now carries
  gt_mask_rle/pred_mask_rle alongside the box (which is display-only — matching
  used masks, not it). scripts/diagnose_detection_image.py (built the same
  round, for a real "why didn't these two obviously-overlapping things match"
  question during review) recomputes the actual mask-IoU matrix from these via
  pycocotools, rather than showing a box approximation that can legitimately
  disagree with the real verdict — which is exactly what motivated dropping
  box matching in the first place, so showing it in the diagnostic would have
  been the same mistake twice.
- Test fixtures were unified rather than duplicated: gtbox()/inst() (used by
  ~90 pre-existing checks) now build a real mask_rle from a FILLED RECTANGLE
  matching the given bbox. A filled rectangle's mask IoU against another
  filled rectangle is mathematically identical to those same rectangles' box
  IoU, so every prior assertion still holds while now genuinely exercising
  mask-only code with no fallback. Shape-specific fixtures (diagonals, etc.)
  stay separate, since a bbox literally cannot describe them.

RESOLVED IN v18 (decided per Pau):
- FIXED a real vision-encoder OOM that occurred on BIG-5 (Twitter) at
  batch_size=24 but did NOT reproduce on ImageNet/Places at batch_size=32 —
  same model, same GPU, same max_model_len. The failing traceback landed
  inside vllm's pixtral.py vision_encoder -> scaled_dot_product_attention
  with "CUDA out of memory. Tried to allocate 1.41 GiB" — i.e. the VISION
  encoder's own attention over image patches, not the text KV cache, which
  ruled out max_model_len/batch_size as the direct cause.
  ROOT CAUSE: nothing anywhere in this pipeline resized images.
  vlm_models.VLLMBackedVLM._encode_image read the raw file bytes straight
  off disk and base64-encoded them as-is. ImageNet/COCO/Places images are
  typically already modest (pre-resized benchmark images), but BIG-5's
  Twitter/Weibo images are raw social-media downloads — arbitrary
  phone-camera/screenshot resolutions with no upper bound. A vision encoder
  like Pixtral scales its patch count (and therefore attention memory,
  QUADRATICALLY in patch count) with input resolution rather than
  processing every image at one fixed small square the way a CLIP-style
  encoder does — so a single oversized raw image in a batch can dwarf the
  memory footprint of an entire batch of already-small ImageNet images,
  independent of batch_size.
  FIX: new --max_image_side CLI flag (default 1024, 0 disables), threaded
  into VLLMBackedVLM.__init__ as an explicit named parameter (kept OUT of
  **kwargs specifically so it's never accidentally forwarded to vllm's own
  LLM(...) constructor, which has no such argument and would raise on an
  unexpected kwarg). _encode_image now checks each image's size before
  encoding and downscales (preserving aspect ratio, LANCZOS resample, .
  convert("RGB") first to avoid palette/CMYK color bugs) any image whose
  longest side exceeds the cap, re-encoding as JPEG quality=90 (not PNG —
  PNG is lossless and can be dramatically larger for photographic content).
  FAST PATH for images already under the cap (true for most ImageNet/COCO/
  Places images, and many BIG-5 images too): Image.open() only reads the
  file header to get .size, not the full pixel data, so checking size is
  cheap, and when no resize is needed the original file bytes are read and
  base64-encoded directly with zero PIL decode/re-encode cost — matters at
  this project's eventual 2M-image production scale, where paying a PIL
  round-trip on every single image regardless of need would be wasteful.
  Verified directly: a synthetic 4000x3000 "raw photo" downscales to
  1024x768 and its encoded payload drops from ~189KB to ~13KB, while a
  synthetic 256x224 "pre-resized benchmark image" passes through
  byte-identical (fast path confirmed taken); --max_image_side 0 reproduces
  the exact old (unresized) behavior for anyone who wants to opt out (e.g.
  already pre-resized their own images). Wired into both
  run_vlm_pipeline.py and evaluate_taxonomy_labeling.py (both create a VLM
  the same way).

  Root cause of the first was NOT the ranking but the lookup: wn.synsets("café")

  adjective, not the class. Validated over all 96 templates x 10 class names

  dependency to a hard requirement of the default path. HISTORY TO KEEP IN
  MIND: v8 added this, v10 reverted it because Pau saw a ClipMatch drop and
  suspected it — but that was never isolated and was confounded with a
  concurrent MetaCLIP switch. If a ClipMatch change shows up now, isolate this
  from any backend swap before attributing it, so the v10 ambiguity is not
  repeated a second time.

RESOLVED IN v14 (decided per Pau):
- MetaCLIP 2 (facebook/metaclip-2-worldwide-huge-quickgelu, ViT-H-14-quickgelu-
  worldwide) added to clip_metrics.CLIP_PRESETS as "metaclip2" — a from-
  scratch multilingual (300+ languages) successor to MetaCLIP 1 ("metaclip"
  preset above), not a fine-tune of it. Native transformers `MetaClip2Model`/
  `MetaClip2Processor` (auto-dispatched via AutoModel/AutoProcessor), NO
  trust_remote_code needed — same hassle-free category as SigLIP2/the LAION
  checkpoints, not FG-CLIP2's custom-init risk. Needs transformers>=4.56.0
  (when MetaClip2 was merged upstream), already covered by this project's
  transformers>=5.14.1 floor. MetaClip2Model mirrors CLIPModel's own
  submodule shape (text_model+text_projection, vision_model+
  visual_projection), so CLIPScorer needed zero new code, same as the LAION
  checkpoints (v9).
- ClipMatch's CANDIDATE-side (GT-class) text/embedding is no longer the
  single OBJECT_TEMPLATE phrase by default — it's the MEAN of a fixed
  prompt-template ensemble per class, L2-renormalized after averaging (the
  "prompt ensembling" recipe from Radford et al. 2021's own zero-shot
  notebooks). Two separate template sets, picked by dataset
  (clip_metrics.CLIPMATCH_CANDIDATE_TEMPLATES): the official 80-template
  OpenAI CLIP ImageNet ensemble (clip_metrics.OPENAI_TEMPLATES) for
  imagenet, and a new 15-template clip_metrics.SCENE_TEMPLATES for
  places365. The ImageNet templates are explicitly OBJECT-recognition
  phrasings (sculptures, tattoos, origami, embroidery, video-game
  renders, plushies) validated for ImageNet-style object classes, not
  scenes — reusing them for Places365 would produce nonsensical text like
  "the plushie kitchen" or "a tattoo of an airport terminal". The original
  CLIP paper only used 2 bare templates for SUN397 (scene recognition);
  SCENE_TEMPLATES improves on that with contextual-anchoring phrasings
  ("a photo of a {}, a type of place.", "a scene taken in a {}.") plus
  camera-quality/lighting variants, while deliberately dropping every
  ImageNet template whose framing doesn't apply to a place (no
  sculpture/tattoo/origami/plushie/video-game-render analogues for scenes).
  Computed ONCE per candidate class (encode_candidate_vocab_ensemble) since
  the candidate vocab never changes mid-run — not recomputed per image.
  Per-image extracted-object text (Object-CLIPScore, ClipMatch's
  anchor-object similarity search) is UNCHANGED, still the single
  OBJECT_TEMPLATE — running an 80-embedding ensemble per extracted entity
  per image was never proposed or validated and would be a real cost at
  2M-image scale for no measured benefit (the ensemble is specifically an
  OpenAI zero-shot-classification technique for a FIXED, small candidate
  set, which the extracted-object side is not).
  --use_wordnet_definitions_clipmatch (v11/v12) is a separate, still-opt-in
  flag that bypasses the ensemble entirely (a single richer text per class
  instead) — unaffected by this change.
- hP/hR/hF1/Wu-Palmer (Section 8f) are now reported as mean ± population
  standard deviation, not just mean, in both summary["hierarchical"] and
  summary["hierarchical_mapped"] (`hp_std`/`hr_std`/`hf1_std`/`wup_std`) —
  a mean alone doesn't distinguish "every image scores close to this" from
  "wildly bimodal, half near 0 and half near 1".

RESOLVED IN v7 (decided from empirical comparison, same day as the
