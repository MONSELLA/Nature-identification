===============================================================
0. IMPLEMENTATION STATUS (NEW in v4)
===============================================================

The VLM pipeline is coded end-to-end. Entry point:
scripts/run_vlm_pipeline.py (--stage all|infer|score). Core logic:
src/vlm_pipeline.py; prompts/schemas: src/models/prompts.py; VLM
backends: src/models/vlm_models.py; dataset loaders + mapping vocab:
src/loaders/dataset_loader.py; taxonomy graph: src/loaders/
excel_loader.py; metrics: src/evaluation/{clip_metrics,taxonomy_metrics}.py.

Key implemented shape (details in the sections below):
  - Two-pass: open caption -> structured extraction (Sections 4-5).
  - Mapping happens in PHASE-1 INFERENCE (not scoring): each extracted
    object is mapped to the taxonomy FIRST, then the VLM labeling call
    is ROUTED (Section 6):
        unmapped        -> ONE full VLM call (nature+biotic+material)
        mapped-nature   -> material-only VLM call (nature/biotic from map)
        mapped non-nature -> NO VLM call
    Every extracted object is labeled on all three axes.
  - --max_hops CLI arg bounds how far an extracted object may resolve
    onto the taxonomy (0 = only annotator-labeled nodes; default 3).
  - --stage all runs infer and score in SEPARATE spawned subprocesses,
    so the VLM's VRAM is released (OS reclaim on process exit) before
    CLIP loads; a shared W&B run id keeps both in one run.
  - Axis scoring differs by dataset type (Section 8): single-label
    (ImageNet/Places) uses the forced top-1 ClipMatch class's taxonomy
    for nature/biotic + VLM material of the best-matching object;
    COCO/BIG-5 use image-level nature (OR) + matched-object axes.

STILL DESIGN-ONLY (not built): the Grounding pipeline (Section 9, and
the COCO box-IoU matching noted in Section 8), and the ablations
(Section 7).

===============================================================
1. TWO SEPARATE PIPELINES (KEY TERMINOLOGY)
===============================================================

  A) VLM PIPELINE (language-based; IMPLEMENTED — see Section 0):
     1. Open-ended caption generation
     2. Structured object extraction
     2b. Map each extracted object to the taxonomy (WordNet mapping
        vocab) BEFORE labeling — routes the labeling call (Section 6)
     3. Taxonomy labeling (nature/no-nature, biotic/abiotic,
        material/immaterial) — mapping when possible, VLM reasoning
        otherwise, routed per object (see Section 6)
     Produces a full per-image prediction scoreable with standard
     accuracy/precision/recall/F1, same framework as the closed-set
     baselines already built.

  B) GROUNDING PIPELINE (geometric/embedding-based; designed, not
     yet implemented):
     1. Thing/stuff geometric routing — Grounding DINO 1.5 + SAM
        for discrete objects ("things"); CLIPSeg-style dense
        segmentation for amorphous regions ("stuff"). Routing is
        geometric (boundable vs amorphous), NOT taxonomic —
        material/immaterial does not align with thing/stuff (e.g.
        a stuffed rabbit is immaterial but geometrically a "thing")
     2. Dual-branch verification — detector/segmenter confidence +
        hierarchy-based margin check via FG-CLIP2 (cosine similarity
        across target/hypernym/sibling hyponyms on localized crops).
        CAVEAT (v6): FG-CLIP2 was tried for the VLM pipeline's CLIP
        scoring and abandoned — its trust_remote_code __init__ crashes
        with a meta-tensor error under this project's transformers
        version (Section 11). Re-verify it loads at all before building
        this step around it; may need a different CLIP backend here too.
     3. Taxonomy-attribute spatial aggregation — per-object
        localization maps combined into biotic/abiotic and
        material/immaterial heatmaps.
        OPEN QUESTION (raised by Pau): worth reassessing whether
        this is actually valuable to implement, vs. lower priority
        than the other Grounding pipeline components — not yet
        decided either way.
     4. Nature importance score (NEW): once nature-related elements
        are segmented via CLIPSeg/SAM, compute the fraction of
        total image pixels belonging to nature-related segments —
        a 0-to-1 score reflecting how much of the image nature
        occupies. Proposed refinement (not yet designed): weight
        central pixels more heavily than peripheral ones, on the
        reasoning that centrally-placed content is more likely to
        be the compositional focus of the image. Exact weighting
        scheme (e.g. distance-from-center falloff function) still
        to be defined.

The rest of this document is organized around the VLM pipeline
(Sections 2-8), since that's what's actively being built. The
Grounding pipeline's role in FINAL cross-VLM metrics is in
Section 9.

3. SERVING / FRAMEWORK DECISIONS
===============================================================

- Context files go in the "system" role (fixed, cacheable,
  behavioral), not "user" (variable, per-call, read as a request).
- vLLM prefix caching (--enable-prefix-caching) to be confirmed ON
  with Ramin — makes the always-present protocol cheap at 2M-image
  scale rather than reprocessed every call.
- Different system prompts per stage = different cache prefixes
  (fine; confirm Ramin's serving config allows this).
  IMPLEMENTED: three distinct system prompts — caption/extraction
  (nature definition only), unmapped-labeling (all three definitions),
  mapped-nature material-only labeling (material definition only) —
  so each is a stable, separately-cacheable prefix.
- Files read from disk once at startup, not per-call, so the token
  sequence stays stable (identical string = cache hit).
  IMPLEMENTED: build_system_prompts() reads the definition files once
  in phase_infer; run_inference reuses the fixed strings per batch.
- IMPLEMENTED (VRAM): --stage all runs infer and score in separate
  'spawn' subprocesses. When the infer subprocess exits, the OS
  reclaims the VLM's GPU memory in full before CLIP loads — more
  reliable than the earlier in-process unload_vlm (vLLM/torch do not
  release CUDA memory dependably on GC). Only the picklable args
  Namespace crosses the boundary; a shared W&B run id (resume="allow")
  keeps both subprocesses logging into one run.
- DSPy: protocol text maps to a Signature's "instructions" field;
  underlying calls still hit vLLM, caching still applies.
- Need to empirically verify smaller models (e.g. Qwen3.5-0.8B)
  actually follow system-prompt instructions reliably — not
  assumed, to be tested.

===============================================================
4. VLM PIPELINE — CAPTIONING STRATEGY (BASELINE)
===============================================================

- BASELINE = two-pass: fully open-ended caption generation (no
  schema at all) → separate call for structured extraction.
  Chosen over single-pass-with-schema-from-the-start because
  forcing structure immediately risks collapsing the caption into
  a checklist-style output, which would make the faithful
  F-CLIPScore and Object-CLIPScore metrics converge and stop being
  meaningfully different.

- Caption prompt (baseline, NEUTRAL — no nature-priming).
  ORIGINAL DESIGN (v1-v6 of this recap): "Describe this image in 3-4
  sentences, covering the main subject, the background, the setting,
  and any secondary elements present. Be specific but concise."
  Reasoning: plain "describe the scene" suffers from (a) salience
  bias (only prominent subject described) and (b) brevity bias
  (short captions leave no room for secondary elements). This prompt
  addresses both without leading toward nature specifically.
  SUPERSEDED (v7 — CLAUDE.md updated to match): the shipped baseline
  is now the shorter "Describe this image, including any text."
  (src/models/prompts.py CAPTION_PROMPT), a deliberate change to
  cover BIG-5's text-heavy/meme/screenshot images (a bare "describe
  this image" skips on-image text entirely). The salience-bias/
  brevity-bias mitigation the original 3-4-sentence prompt provided
  is NOT carried over by this shorter prompt — not yet re-validated
  empirically post-switch; worth confirming via F-CLIPScore/
  Object-CLIPScore whether that mitigation is still needed once
  real per-model captions are in hand.

- Explicit decision: do NOT add "pay special attention to nature-
  related elements" to the baseline. Reasoning: leading question →
  risk of hallucinated compliance (model invents nature-adjacent
  content because it was asked to look for it) — directly relevant
  since this is the exact failure mode F-CLIPScore/OHD-Caps
  research targets. Nature bias already present via the system-
  level definition file.
  → Proposed as an ABLATION axis instead (Section 7), to be
  settled empirically via F-CLIPScore/Object-CLIPScore rather than
  assumed.

5. VLM PIPELINE — EXTRACTION STRATEGY
===============================================================

Two ways to do extraction — both planned as part of the ablation
study, undecided which is default:
  a) same VLM does both caption + extraction (multi-turn) —
     simpler, faster to ship, but conflates visual understanding
     quality with instruction-following/schema-adherence quality.
     ADDED BENEFIT (Pau): re-sending the image to the VLM during
     the extraction call gives the model a second look, which may
     surface objects omitted from the free-form caption the first
     time around.
  b) caption by VLM, extraction by a separate fixed agnostic LLM
     (constant across all VLMs benchmarked) — decouples visual
     perception from extraction compliance, cleaner for the Goal-1
     cross-VLM comparison.
Plan: build (a) first for week-1 speed, formally compare vs (b)
once the pipeline exists.
IMPLEMENTED: (a) — the same VLM captions and extracts (extraction
re-sends the image, the "second look"). (b) remains an ablation
(Section 7), not yet built. Extraction uses a structured schema
(ObjectExtractionResponse) returning a de-duplicated object list.

CONSTRAINT ON THIS ABLATION: material/immaterial labeling
(Section 6) cannot be handed to a text-only agnostic LLM regardless
of what wins here — it requires image access (see Section 6). So
even if (b) wins for extraction/object-naming, material/immaterial
classification specifically must stay VLM-based. Not a fully open
50/50 comparison for that one axis.

===============================================================
6. VLM PIPELINE — TAXONOMY LABELING STRATEGY
===============================================================

Hybrid approach, applying the pre-existing project principle that
biotic/abiotic (and nature/no-nature) is inheritable via WordNet
hop distance, while material/immaterial is NOT (depends on
real-instance-vs-representation — requires per-instance reasoning,
not just concept lookup):

  - NATURE/NO-NATURE and BIOTIC/ABIOTIC: use WordNet mapping when
    the object falls in the mapped vocabulary (ImageNet/COCO/
    Places); fall back to VLM reasoning when unmapped. Applies to
    BOTH axes equally — both are hop-derivable from a mapped GT
    node.

  - MATERIAL/IMMATERIAL: ALWAYS use VLM reasoning, never mapping —
    a "tree" node has no way of encoding whether THIS image shows
    a real tree, a painting, or a video-game tree. No mapping-based
    alternative exists for this axis.

  - IMPORTANT: VLM labeling is IMAGE-SUPPORTED, not text-only — the
    model has the image available when doing the labeling
    reasoning, not just the extracted object string. Specifically
    crucial for material/immaterial (a bare word "tree" cannot
    disambiguate real/painted/video-game; the pixels can). Drives
    the constraint in Section 5 — material/immaterial can't be
    delegated to a text-only agnostic LLM.

IMPLEMENTED (routing + where it runs):
  Mapping runs in PHASE-1 INFERENCE, BEFORE the VLM labeling calls
  (not deferred to scoring — saves compute and the artifact ships
  fully resolved). Each extracted object is mapped via the dataset's
  authoritative class->synset table (build_mapping_vocab; no
  word-sense guessing), then the labeling call is ROUTED:
    - UNMAPPED object -> ONE full VLM call, all three axes at once
      (TaxonomyResponse; system prompt = all three definitions).
    - MAPPED-nature object -> MATERIAL-ONLY VLM call (MaterialResponse;
      system prompt = material definition only). nature/biotic taken
      from the mapping, so the VLM is not asked to re-derive them.
    - MAPPED non-nature object -> NO VLM call (nature=False from the
      map; biotic/material are n/a).
  Two batched generate_batch calls per image-batch (one per system
  prompt) keep each prefix cache-friendly. EVERY extracted object ends
  up labeled on all three axes.

  --max_hops (CLI) bounds how far an extracted object may resolve onto
  a labeled taxonomy node (TaxonomyGraph.resolve_labels): 0 = only a
  directly-annotated synset counts (no inherited label); 1 = also one
  hypernym/hyponym hop; default 3. Stored in the artifact header and
  reused by --stage score. Lower values push more objects to the VLM
  fallback; higher values map more aggressively.

VALIDATION / CALIBRATION:
  Rather than an ablation comparing "mapping-first" vs "always use
  VLM," directly measure classification calibration: have the
  model classify GT-mapped CLASS NAMES ONLY (no image, no
  extraction involved) against the WordNet-derived labels for
  nature/no-nature and biotic/abiotic. This isolates pure
  taxonomic-reasoning reliability from object-recognition ability,
  and gives a clean number for "how much can we trust VLM fallback
  when mapping is unavailable."
  ASSUMPTION TO STATE EXPLICITLY: this assumes reliability on
  canonical dataset class names transfers to messier real-world
  BIG-5 objects — a transfer assumption, not proven by the check
  itself.

THREE DISTINCT ACCURACY LAYERS (do not collapse into one number):
  1. Extraction accuracy — did the GT object get mentioned at all
     (Section 8a-c)
  2. Classification calibration — class name → taxonomy label vs
     WordNet GT, no image, no extraction (this section, above)
  3. End-to-end mapped-subset accuracy — full image pipeline,
     filtered to GT-mapped classes (compounds extraction quality +
     classification quality; reflects real-world pipeline behavior,
     NOT a clean reasoning-only number — the mapped subset's
     accuracy still depends entirely on whether the model correctly
     identified the element in the image first)
  Report all three separately, clearly labeled — they answer
  different questions and conflating them hides which part of the
  pipeline (recognition vs reasoning) is responsible for errors.

===============================================================
8. METRICS FOR VLM PIPELINE SELECTION
===============================================================

--- Reference-free (fast iteration, any image, no GT needed) ---

a) F-CLIPScore (faithful replication, Oh & Hwang — "Vision-
   Encoders (Already) Know What They See" / F-CLIPScore paper):
     F-CLIPScore(S) = [CLIPScore(S) + sum_i CLIPScore(n_i)] / (N+1)
   S = full caption sentence, n_i = individual extracted objects
   (N of them). Requires the caption (sentence term). NOT novel to
   us — cite exactly as their method when implemented per Eq. 1.

b) Object-CLIPScore (OUR variant, F-CLIPScore-INSPIRED, NOT
   identical — must be described precisely, never called
   "F-CLIPScore"): average CLIPScore over extracted objects ONLY,
   template "a photo of a {object}", NO sentence-level term. Their
   ablations never test dropping the sentence term — must be
   attributed as an adaptation. Underlying object-level insight is
   theirs (cited); the specific simplified formula is ours.

KNOWN LIMITATION (inherited, not introduced by us): CLIPScore-family
metrics compare against the WHOLE image embedding, not a localized
crop — a plausible-but-absent object can score deceptively well.
Even the original paper's best untrained noun-level variant trails
trained methods by 17.6-37.4 points on OHD-Caps. Explicitly
first-pass proxies, not substitutes for the Grounding pipeline's
localized verification.

CRITICAL PRACTICAL ISSUE — CLIP 77-TOKEN LIMIT:
Standard CLIP text encoders truncate at 77 tokens; only ~20 tokens
reliably well-trained per Long-CLIP's analysis. Conflicts with the
detailed-caption strategy (Section 4) for the sentence-level term.
Object-level terms unaffected (short templated phrases).
Mitigation options (not yet decided):
  - Long-context CLIP variant for the sentence-level term. FG-CLIP2
    was tried (it explicitly trains on long-caption modeling, unlike
    vanilla CLIP) and ABANDONED — see Section 11 — its
    trust_remote_code __init__ crashes with a meta-tensor error under
    this project's transformers version. Jina-CLIP-v2 (now in
    CLIP_PRESETS) handles much longer text and may be worth trying
    for this specifically; alternatively Long-CLIP (still not
    packaged as a plain HF AutoModel — see CLIP_PRESETS's comment).
  - Accept + document truncation as a stated limitation
  - Deliberately truncate/cap captions at a controlled length

F-CLIPScore/Object-CLIPScore reward PLAUSIBILITY, not
EXHAUSTIVENESS — insufficient alone to pick the final config (a
pipeline extracting only a few "safe" objects can score well while
missing most real content). ADDED (Pau): for this reason, track and
report the TOTAL NUMBER of objects detected/extracted per model as
a companion diagnostic — a model scoring well on F-CLIPScore/
Object-CLIPScore while extracting very few objects overall is a
red flag for under-extraction, not a sign of a well-calibrated
pipeline. Must be paired with GT-based checks below (two-tier
validation: cheap proxy for broad iteration, GT checks to confirm
the winning configuration).

--- GT-based (confirm final configuration) ---

c) BIG-5 nature Yes/No accuracy: map extracted objects through
   WordNet; nature=1 if ANY object maps to a nature node, else
   nature=0. Compare against the BIG-5 GT annotations (image-level,
   usable even without a full object dictionary mapped). Report
   OBJECT-MAPPING HIT RATE (% of extracted objects that map to
   WordNet at all) alongside it as a diagnostic — low hit rate
   means "no nature" errors may reflect vocabulary-mapping gaps,
   not genuine model failure to notice nature.

   EXTENDED (Pau): since the VLM pipeline includes a VLM fallback
   for unmapped objects by design (Section 6), this fallback can be
   used from the start, not just as an unmapped-case patch — every
   extracted object gets a nature/no-nature, biotic/abiotic, and
   material/immaterial label regardless of mapping status (mapped →
   WordNet-derived label; unmapped → VLM-derived label). This means
   full accuracy — not just nature Yes/No, but also biotic/abiotic
   and material/immaterial — can be computed across ALL datasets
   (BIG-5, COCO, ImageNet, Places), not only where mapping succeeds.
   Track WordNet-mapping-rate vs. VLM-fallback-rate throughout, so
   it's always clear how much of any reported accuracy number rests
   on deterministic mapping vs. VLM judgment.

d) COCO/ImageNet/Places — GT-mention accuracy (EM/Contains, per
   Ging et al.'s O-VQA framework, applied to extracted-object-lists
   instead of free text — cite as such): check whether the GT class
   or any WordNet-synset synonym (not just the literal label
   string) appears among extracted objects.

e) ClipMatch (Ging et al.-inspired), ImageNet + Places ONLY —
   COCO/BIG-5 excluded (COCO multi-label, BIG-5 has no closed class
   vocabulary — ClipMatch needs a fixed candidate list, so this
   scoping is a correctness requirement, not a compromise):
     - SUPERSEDED IN v5 (see below): originally run against the
       EXTRACTED OBJECT LIST (max similarity across independently-
       embedded objects per candidate) with the raw-caption and
       concatenated-object-sentence variants explicitly REJECTED for
       token-limit + semantic-dilution reasons (kept below for
       history). After both variants were actually implemented and
       compared empirically, the CAPTION-based version performed
       better — so as of v5 it is the ONLY ClipMatch implementation;
       the object-list code has been removed from clip_metrics.py.
     - CURRENT (v5): score the WHOLE CAPTION's CLIP embedding
       against each candidate class directly; argmax = predicted
       class (clip_metrics.clipmatch). The 77-token truncation risk
       this reintroduces (see the original rejection rationale below)
       is accepted as a stated limitation given the empirical gain.
     - ORIGINAL (v1-v4) DESIGN, kept for history — run against the
       EXTRACTED OBJECT LIST, not the raw caption and NOT a
       concatenated sentence template ("a photo of a X, a Y, and a
       Z" was considered and rejected — see below):
         - Score each extracted object independently via its own
           short phrase ("a photo of a {object}"), take the MAX
           similarity across all objects as the model's implicit
           best guess for each GT candidate class.
         - REJECTED APPROACH — raw caption: risks CLIP 77-token
           truncation on long captions, and ClipMatch was designed/
           validated on short single-answer VQA responses, not
           multi-sentence scene descriptions — using the full caption
           deviates from how the metric was built and tested. (This
           is the approach v5 above ended up adopting anyway, after
           empirical comparison showed it outperforming the
           object-list version despite this caveat.)
         - REJECTED APPROACH — concatenated object-list sentence ("a
           photo of a X, a Y ... and a Z"): (1) still risks the
           77-token limit with busy scenes (8-10+ objects), worse
           than the caption case since triggered by object count not
           verbosity; (2) semantic dilution — one joint embedding for
           many objects is a smeared average, diluting the signal for
           any single target GT class, hurting matching precisely in
           richer scenes. (Still not used — this rejection stands.)
     - CANDIDATE-SIDE text (v11, OPT-IN, separate from all of the
       above — those are all about the IMAGE-description side):
       `--use_wordnet_definitions_clipmatch` swaps each GT candidate
       class's plain OBJECT_TEMPLATE phrase ("a photo of a golden
       retriever") for its WordNet lemma(s) + gloss in natural prose
       (clip_metrics.wordnet_definition_text — "A golden retriever,
       also known as ... . It is defined as: <definition>."). NOT the
       default; not yet empirically validated either way. See
       RESOLVED/PROPOSED IN v11, Section 11.

f) Hierarchical Precision / Recall (hP/hR) + Wu-Palmer, per
   Snæbjarnarson et al.'s taxonomy-aware evaluation — ImageNet +
   Places ONLY (same scoping rationale as ClipMatch, e above):
     - Captures GRANULARITY CREDIT that EM/Contains cannot: e.g.
       predicting "canine" when GT is "golden retriever" scores
       flatly wrong under Contains, but hP/hR gives partial credit
       for the correct branch of the tree.
     - Directly demonstrates (rather than just cites) the
       granularity-mismatch failure mode already discussed in the
       SOTA review (Yu et al.'s fine-grained-task finding).
     - Method: take the predicted GT class from ClipMatch (e,
       above), then map it onto a WordNet node via the extracted
       object list and compute hP/hR against the GT node.
     - IMPLEMENTED (taxonomy_metrics.resolve_to_wordnet): the
       predicted-class -> WordNet-node step is NOT a BGE cross-encoder
       (that was the design sketch). Instead the extracted objects are
       ranked by their CLIP similarity to the predicted class (each
       extracted object's embedding dotted against the ClipMatch-
       predicted class's own embedding — computed in run_vlm_pipeline.py
       right after the v5 caption-based ClipMatch call, since ClipMatch
       itself no longer touches per-object embeddings), the top phrase
       that resolves in WordNet is taken, and polysemy is broken by
       maximizing Wu-Palmer similarity to the predicted class. hP/hR
       are then the ancestral-closure overlap of GT node vs. predicted
       node (compute_hierarchical_metrics).

Report BOTH EM/Contains (strict) and hP/hR (graded closeness) per
dataset — they answer different questions; together they give a
richer results table (exact-match rate + how far off misses were)
than either alone.

IMPLEMENTED — AXIS SCORING (nature/biotic/material acc/P/R/F1),
SPLIT BY DATASET TYPE:
  - ImageNet/Places (single-label): nature/biotic are read off the
    FORCED top-1 ClipMatch class's taxonomy position — NOT lexical
    extraction matching, NO similarity threshold (global argmax over
    the full candidate vocab always returns a class). This fixes a
    real bug: ORing nature across every extracted object penalized a
    correctly-detected incidental object (e.g. a real cat in a
    GT-"couch" image). Robust to species-level mismatch (GT "golden
    retriever" vs. pred "dog" still agree on nature/biotic).
    material stays the VLM's own label (never mapped, per this
    section's rule) — taken from the best-matching extracted object.
  - COCO (multi-label) + BIG-5 (holistic scene): image-level nature =
    OR over extracted objects; biotic/material scored on the matched
    GT object (lexical class-name/synonym match).
    FUTURE WORK (needs the Grounding pipeline): replace COCO's lexical
    matching with Hungarian box-IoU assignment (IoU>=0.5) once
    Grounding DINO 1.5 gives predicted boxes — matched GT boxes score
    as usual; unmatched GT boxes penalized as wrong; unmatched
    PREDICTED boxes EXCLUDED not penalized (COCO's 80 classes are a
    curated subset, so an extra real object is not a hallucination).
    A TODO to this effect is left in run_vlm_pipeline.py.
  - "extraction-hit rate" (exact-match: was the GT object mentioned)
    is kept as a REPORTING-ONLY diagnostic; it no longer gates or
    feeds any axis score.

9. GROUNDING PIPELINE — ROLE IN FINAL CROSS-VLM METRICS (GOAL 1)
===============================================================

Purpose: NOT for validating the VLM pipeline internally — for
producing the final metrics comparing different VLMs' nature-
identification performance across all available datasets, once
both pipelines exist.

Plan: combine (i) existing GTs (COCO/ImageNet/Places mapped vocab +
BIG-5 annotations) with (ii) reference-free verification of
VLM-claimed objects falling OUTSIDE the GT/mapped vocabulary, using
Grounding DINO (open-vocabulary detection) + the CLIP margin-check
idea, to check plausibility of e.g. a claimed "tree" not in GT.

Framing decisions:
  - DINO+CLIP check = agreement with an INDEPENDENT open-vocabulary
    detector, NOT ground truth — must be described this way
    explicitly (the detector has its own biases/error modes).
  - Report GT-recovery and verified-extra-content as TWO SEPARATE
    numbers, not merged — merging risks unfairly rewarding/
    penalizing verbose vs conservative models depending on
    weighting.
  - Since this check feeds the headline cross-VLM comparison, a
    SMALL MANUAL AUDIT (~50-100 images, human-checked) is planned
    to validate the DINO+CLIP verifier's own agreement/error rate.

Separately (VLM pipeline selection context, Section 8): extending
WordNet mapping beyond the three fixed dataset vocabularies (map
only the NOVEL object names the VLM actually extracts, not the
whole dictionary upfront) proposed as a way to shrink the
unmapped-object gap directly, cost permitting.

RESOLVED IN v6 (decided after repeated integration failures):
- FG-CLIP2 (qihoo360/fg-clip2-large) is ABANDONED as a CLIP backend
  and removed from clip_metrics.CLIP_PRESETS. Its trust_remote_code
  __init__ builds a positional-embedding mask (`mask1`/`mask2`) as a
  plain tensor attribute rather than a registered nn.Parameter/
  nn.Buffer. Under this project's transformers version, __init__ runs
  inside a meta-device "fast init" context regardless of any loading
  kwarg (torch_dtype, low_cpu_mem_usage, device_map — all tried, none
  fixed it, including loading exactly per FG-CLIP2's own HF model-card
  example with no extra kwargs at all), so that tensor never gets real
  data and the first text-encoding forward pass crashes with
  `NotImplementedError: Cannot copy out of meta tensor; no data!`. A
  dedicated (non-generic) loading class was also tried and hit the
  identical crash, confirming this is a genuine incompatibility between
  FG-CLIP2's own trust_remote_code and this transformers version, not
  something fixable from the calling side. clip_metrics.py's `walk_type`/
  `_text_walk_type` handling (added earlier to work around a DIFFERENT,
  separate FG-CLIP2 issue — its get_text_features() needing a
  walk_type kwarg tied to a fixed 64/196-token sequence length) has
  been removed along with it, since it's moot without a working load.
  SigLIP2 (google/siglip2-base-patch16-224, native transformers, no
  trust_remote_code needed) and Jina-CLIP-v2 (jinaai/jina-clip-v2,
  trust_remote_code, RAW string/image input convention — see
  clip_metrics.CLIPScorer's class docstring) were PROPOSED as
  replacements here, but neither was actually added to CLIP_PRESETS at
  the time — see RESOLVED IN v8 below for what's actually wired in.

RESOLVED IN v12 (measured, per Pau):
- The v11 WordNet-definition ClipMatch candidate text
  (`clip_metrics.wordnet_definition_text`, `--use_wordnet_definitions_clipmatch`)
  was run and compared against the plain OBJECT_TEMPLATE phrase — NO
  MEANINGFUL DIFFERENCE in ClipMatch top-1 between the two. The
  "richer candidate-side semantic content aligns better against a
  VLM's own descriptive summary" hypothesis (v11) is NOT supported by
  this result. Kept in the codebase as a non-default, opt-in flag
  (cheap to keep, not proven harmful either, and may behave
  differently on a larger sample or a different CLIP backend) rather
  than removed outright — unlike the inflect-determiner change (v10),
  which was reverted because it was suspected of actively hurting the
  score. If revisited, a larger sample than the earlier spot-check
  runs would be needed to rule out this being a real-but-small effect
  hidden by run-to-run noise (see the earlier non-determinism
  discussion) rather than a genuine null result.

v11 PROPOSAL (for reference — see RESOLVED IN v12 above for the outcome):
- ClipMatch candidate-vocab text got an independent, opt-in variant:
  `clip_metrics.wordnet_definition_text(synset_id)` builds "A {primary
  lemma}, also known as {other lemmas}. It is defined as: {WordNet
  gloss}." per GT candidate class, instead of the plain OBJECT_TEMPLATE
  phrase. `clip_metrics.candidate_vocab_texts(..., use_wordnet_definitions=...)`
  picks between the two; wired to run_vlm_pipeline.py's
  `--use_wordnet_definitions_clipmatch` (--stage score only — the
  choice doesn't affect --stage infer at all). Every candidate's
  synset_id is guaranteed to resolve via `wn.synset()`
  (get_candidate_vocab's own docstring), so no mapping-fallback logic
  is needed here the way it is for object-side WordNet lookups
  (resolve_to_wordnet). Needs `inflect`, but ONLY for this path — the
  OBJECT_TEMPLATE default was reverted off inflect in v10 (below) and
  is unaffected. Token-length/truncation diagnostics
  (summary["clipmatch_candidates"]) track whether WordNet glosses risk
  exceeding cm_scorer's context length, since a gloss can run
  considerably longer than "a photo of a {class}".
