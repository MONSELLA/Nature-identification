# --- VLM inference backends (src/models/vlm_models.py) ---
# Every registered model family (qwen/mistral/llava/internvl/gemma) is served
# through vLLM — needs SamplingParams, StructuredOutputsParams
# (vllm.sampling_params — this is the CURRENT vLLM API name; older vLLM
# releases called this GuidedDecodingParams, but that name is gone from the
# code now, so don't go looking for it), and vllm.distributed.parallel_state's
# destroy_model_parallel/destroy_distributed_environment.
# (The HuggingFace-served BLIP/BLIP-2/InstructBLIP/BLIP-3 family and its
# `outlines`-based structured-decoding path were REMOVED — this project only
# evaluates vLLM-served models. Don't re-add `outlines` here unless that
# backend comes back; nothing else in this codebase imports it.)
#
# IMPORTANT — DO NOT re-add an `outlines<1.0.0` upper pin here, and DO NOT
# pin transformers/torch/xformers/outlines to specific versions of your own.
# Doing so caps vLLM at a stale release: `outlines<1.0.0` (previously here)
# forced pip to backtrack to vllm 0.9.2, which (a) crashed on newer
# transformers via the aimv2 config collision and (b) was too old to load
# recent models (Gemma's rope_scaling config -> "rope_scaling should have a
# 'rope_type' key"). vLLM pins its OWN coherent torch/xformers/transformers/
# outlines set — let it win. Give it only a recent FLOOR and stay out of the way.
vllm>=0.10.0
# 5.14.1 floor (higher than vLLM's OWN floor) because the Grounding pipeline's
# SAM3 support (transformers.models.sam3) only exists from 5.14.1 on —
# confirmed present there. If AutoModel.from_pretrained("facebook/sam3")
# raises an unknown-model-type error, this floor is why: upgrade transformers,
# don't chase it as a config problem.
# CHECKED FOR CONFLICT WITH vLLM (this is exactly the kind of pairing that
# broke things before — see the outlines<1.0.0 story above): vLLM's own
# latest PyPI release (0.26.0, checked 2026-07) declares `transformers>=5.5.3`
# with NO upper bound, so pip can freely pick any transformers >=5.14.1 to
# satisfy both constraints at once — no conflict today. This has NOT always
# been true of every vLLM release (older ones have pinned transformers<5 at
# times), so if a future vLLM release reintroduces an upper cap below 5.14.1,
# `pip install -r requirements.txt` will fail loudly (not silently downgrade)
# rather than installing something broken — if that happens, the fix is to
# bump `vllm>=` to a release whose own transformers ceiling clears 5.14.1,
# not to lower this floor (that just reintroduces the SAM3 breakage).
transformers>=5.14.1
torch>=2.1
torchvision>=0.16
Pillow>=10.0
